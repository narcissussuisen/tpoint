一、结论（一句话）

根因 BUGwatchlist 热重载把"新加入"标的的 STATE[sym]['PC'] 清零，而当日 refresh_daily() 不会再跑 → 被恢复进来的 161129 / 513310 的 PC 恒为 0 → detect_for 在 if pc<=0: return 提前空返回，全天零信号。

叠加问题运行中 monitor 是旧代码（metrics 无 code_version 字段，落后于 f730f58），即使 688347 的 PC 保留着有效值，今天也未出信号——运行态与磁盘代码不一致，存在更广泛的静默。需重启 monitor 加载当前磁盘代码（fd26203）方可当日恢复。

已排除发送链路（飞书 webhook）健康：emit_signal→push_batch→_push_retry→requests.post 07-23 仍能成功推送（见 push_audit.jsonl）。本次非"发送阻塞/延迟"，而是"上游检测判定为空"。

二、信号发送调用链路（当前代码）

run() 主循环 (core/monitor.py) └─ → compute(sym) # 拉 mootdx 1m bar + compute_miji_indicators（受 _data_lock 互斥） └─ → _handle_staleness() # 新鲜度校验，陈旧源剔除 └─ → detect_for(sym,...) # ← 信号检测入口 ├─ pc = STATE[sym]['PC']; if pc<=0: return [] # ★ 零信号闸门（PC=0 直接返回空） ├─ 持仓中：硬止损 / 反向平仓 / 移动止损 / 时间止损 └─ 空仓：check_b_trigger / check_s_trigger（floor 门控 + 均线引力 + MACD背离） └─ → _risk_gate() # 顶层风控闸门（HALT_BUY/FORCE_SELL） └─ → emit_signal(s,sym) # 构造飞书卡片 └─ → push_batch(batch) # MIN_PUSH_INTERVAL=5s 节流 └─ _push_retry → requests.post(WEBHOOK_URL) # 飞书信号群 1d241455-... └─ 失败入队 push_pending.jsonl，下轮 _drain_pending 补发

链路在 detect_for 即中断（返回空 batch），故 emit_signal 与飞书推送从未被调用——这与日志只见 本轮无信号、从未见 本轮信号 完全吻合。

五、修复方案

  • 已修（磁盘） core/monitor.py 热重载逻辑：新增标的不再 STATE[s]={'PC':0}，改为立即 refresh_daily(s) 回填昨收（已 py_compile 通过）。防止未来热重载再次清零 PC。
  • 需人工 重启 monitor（宿主机管理员，结束 Session 0 的 pid 6528 旧进程，由 V9Launch.bat / run_monitor.bat 重新拉起）。重启后加载 fd26203 代码并重新 refresh_daily 填 PC → 当日信号即可恢复。注：WorkBuddy 侧无法 kill Session 0 进程，需你在宿主机操作。
  • 可选 给 watchlist 加 suspended_until/status（fd26203 已支持）后，停牌标的走过滤而非"移除+恢复"，可彻底避免本次"清零 PC"路径。
